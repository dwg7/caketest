# 0001: ODbLライセンスへの対応方針

* ステータス: **提案(Proposed)** — 最終決定は人の手に委ねる
  (CLAUDE.md 4節「作業分担」参照)
* 日付: 2026-09-22

## 背景

LayercakeのデータはOSM由来であり、ODbL(Open Database License 1.0)の
下で提供されている。ODbLはシェアアライク型のコピーレフトライセンスで、
主に以下を要求する:

1. **帰属表示(Attribution, §4.3)**: OSMおよびそのコントリビューターへの
   帰属を示すこと。標準的な表記は「© OpenStreetMap contributors」。
2. **シェアアライク(Share-Alike, §4.4)**: ODbL対象データベースに対して
   実質的な処理(substantial processing)を加えて公開する場合、その
   派生データベースも同じくODbLで公開する義務がある。
3. **技術的制限の禁止(§4.6)**: 再配布時にDRM等でデータの自由な利用を
   妨げてはならない。

一方で、これまでdwg7の他プロジェクト(kaga0、zukaku等)はCC0や
"let-go principle"(自由に使ってもらうためライセンスにこだわらない
考え方)を軸にしてきた。ODbLのシェアアライク条項は、この方針と
性質が異なるため、混同しないよう明確な扱いが必要。

## 検討した選択肢

### 案A: 「クエリのみ・再配布なし」に限定する

caketestリポジトリでは、Layercakeのデータを**加工・保存・再配布しない**。
DuckDBでのクエリ結果はその場で確認するのみで、リポジトリには
「どういうクエリを投げて何が分かったか」という調査記録
(`queries/*.sql`、`notes/findings.md`)だけを残す。生データや
大量の抽出結果はコミットしない。

* 長所: ODbLのシェアアライク義務がほぼ発生しない(再配布していない
  ため)。dwg7の既存のCC0方針と衝突しない。
* 短所: 他プロジェクト(kikimimi等)に実際に統合する段階になったら、
  改めてODbL対応を検討し直す必要がある。

### 案B: 抽出データを派生データベースとしてODbLで再配布する

Settlements等から抽出した部分集合を、ODbL付きで別途公開する
(例: `data/`ディレクトリにODbL表記を添えて格納)。

* 長所: 統合先プロジェクトが直接使えるデータを提供できる。
* 短所: シェアアライク義務により、統合先(kikimimi等)がCC0方針を
  維持できなくなる可能性がある。ライセンス表示の実装コストも発生。

### 案C: Produced Work(制作物)として扱い、帰属表示のみで済ませる

ODbLには「Produced Work」(データベースを使って作られた地図・
可視化・分析結果など)は、データベース自体ではないため帰属表示のみで
再配布できるという規定がある(§4.3, §2.4)。集落名の一覧を単純に
複製するのではなく、分析結果・要約統計・判断材料としてのみ活用する
のであれば、この規定が使える可能性がある。ただし「名称と座標の
一覧」をそのまま抜き出すことがProduced Workと言えるかは境界が曖昧。

## 現時点の提案

**段階1・2の調査フェーズでは案Aを採用する。**

* `queries/`には検証用SQLのみを置き、大量データの実体は保存しない
  (このADR作成時点で違反なし: `queries/settlements-*.sql`は
  bbox付きクエリのみ)
* `notes/findings.md`に記載する統計・サンプル行は、帰属表示を
  兼ねて「出典: Layercake (OpenStreetMap US) / OSM contributors,
  ODbL」を明記する
* 段階3で実際に他プロジェクトへの統合(案B相当)を検討する段になれば、
  統合先ごとに改めてADRを起こし、シェアアライク義務をどう満たすか
  (別リポジトリを切る、ODbL表記を統合先に持ち込む等)を人が判断する

## 未決事項(人の判断が必要)

* 統合を決めた場合、統合先プロジェクト(CC0方針のkikimimi等)に
  ODbLデータを持ち込むことの是非
* 帰属表示の具体的な文言・置き場所の標準化
* Produced Workとして扱える範囲の線引き
